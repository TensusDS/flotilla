## Running

G1. **obs — the seats' start-up announcements reach the person's own session.** At 16:41:37–42 every seat's prompt
hook fired (the peers' one-line announcements, arrangement skill step 2 "list them (ListAgents) and send each one
line"), and so did the prompt hook of the person's interactive session `game2048-57` (16:41:39), which is not a seat.
`ListAgents` lists every local session, so "live peers" includes the person's own session (and, by the skill's
wording, any session on the machine; none of the ai-os sessions was seen prompted — not measured beyond this one).
Seats then stopped (Stop hook 16:41:42–47) and stood `working / idle`, waiting for a task: no Stop-guard block,
since a reserved post row is not a move. Fix: announce to the fleet (`flotilla fleet`), not to every listed session.

G2. **obs — the task reached the orchestrator at 17:21:52, and routing took one minute.** The person's prompt fired
the orchestrator's prompt hook at 17:21:52 (its `ask` and `permission` hooks fired at 17:22:08: the orchestrator
asked the person a question, which the ask guard lets through for this post). By 17:22:47 two rows were claimed —
`feat/2048-gui` by main session 2 and `feat/2048-docs-exe` by minor session 39 — so **F12 did not recur**: the minor
took the orchestrator's routed task. The orchestrator assigned the minor's handed row to review session 3 at
17:23:42 and the reader took it at 17:23:51 — 9 s later, so the letter reached an idle reader (**F23 did not
recur** here).

G3. **gap — a dependency the work had was not declared, and the sender caught it by hand.** `feat/2048-docs-exe`
(docs plus a `run_game.py` that imports `game2048.__main__`) was claimed without `--requires` on `feat/2048-gui`,
which holds the package. So the ledger let it go claimed → handed → accepted (review session 3, 24 s after taking it,
at 17:24:15), and only the sender saw that it cannot ship alone: at 17:24:37 it recorded a wait on the gui row's
author — "run_game.py imports game2048.__main__, package exists only on feat/2048-gui; land gui first or together
with docs". The mover's wait is legal now (**F24 did not recur**). But the order lives in a note, not in
`requires`, so `queue` would not refuse it and the judge's path rule (decision 86) cannot see the two rows as one
path. Why it happened: the orchestrator split the task into parallel rows and no one declared the edge. Fix: the
orchestrator's template says to name `--requires` when it splits work whose parts import each other, or `claim`
offers it when a branch imports a module only another open row adds.

G4. **obs — both rows shipped five minutes after the task, by the direct-push sequence (F14, F15 did not recur).**
The sender merged `feat/2048-gui` (12027b3) and `feat/2048-docs-exe` (ab5a993) in its own tree on a branch from
`origin/main`, took the push receipt over ab5a993, pushed once, then recorded `queue` → `land` → `ship` for each at
17:26:42–56 — `land` accepted the merges already on origin while the local trunk in the main checkout stayed at
b8da404, untouched. The judge's prompt hook fired at 17:27:18, 22 s after the second `ship`: the letter reached it
(**F23 did not recur**). Nobody asked the person anything but the orchestrator (`ask` fired only in the
orchestrator's session).

G5. **minor — both rows record the batch head as their trunk commit.** `feat/2048-gui` shows "trunk commit ab5a993",
the docs merge, not its own merge 12027b3: the sender named `--merge ab5a993` for both (without `--merge`, `land`
now picks the earliest commit carrying the revision, decision 87, which would have been 12027b3). Harmless for the
walk — ab5a993 carries both — but the row's record names a commit that also carries another row's work. Fix: the
sender template's step 6 says "`--merge <the merge commit of that branch>`", or `land` warns when the named commit
is not the earliest one carrying the revision.

G6. **bug — `tree switch` refuses the fix row a judge filed, because it has no branch yet.** The judge walked
`feat/2048-gui` (walked 17:29:32, closed by its author 17:29:48 — the path rule did not hold it: nothing `requires`
it, G3) and broke `feat/2048-docs-exe` at 17:29:33 ("walk broke on Q line in the guide"), filing fix row r10
`fix/feat/2048-docs-exe` for minor session 39, with no branch (`show`: "base: no branch yet" — the F22 wording
works). The minor, taking it in its home tree as its post says, ran `flotilla tree switch fix/feat/2048-docs-exe` and
got "git switch fix/feat/2048-docs-exe failed: fatal: invalid reference": `switch` treats an existing row as an
existing branch. (`broke`'s own letter says `flotilla tree cut … --tree <path>`, which the arrangement tells main and
minor not to use.) Fix: `tree switch` on an open row of yours with no branch creates the branch from trunk, as for a
new claim.

G7. **gap — the workaround duplicated the fix, and the row the judge waits on is now orphaned in effect.** The minor
recorded a wait on the orchestrator for r10 at 17:30:06 ("tree switch refused … row r10 has no branch yet") — the
right route, not the person (**F16, F17 did not recur**) — and then claimed a new row r11 `fix/docs-controls` at
17:30:32 for the same fix, handed 17:30:58; the orchestrator assigned it 17:31:09 and review session 3 took it
17:31:18. But the judge waits on r10 ("I re-walk once it ships"), r10 will never carry a commit, and r11 has no
`fixes` link to r9. Expect r10 to need `release --settled-by fix/docs-controls` (decision 85) and the judge's re-walk
to go by r11. To watch.

G8. **obs — a session named `game2048-minor-39-79` appeared among this project's sessions for one tick** (17:31:05,
`guard status`: no hook ever fired) and was gone from the census at 17:31:30. Its name is the minor's tree name
plus a number — probably a session Claude Code raised in the minor's worktree (background isolation or a

G9. **gap — a fix settled by another row leaves the broken row "unfixed", and the judge waiting on the dead row.**
The duplicate fix r11 `fix/docs-controls` went accepted (review session 3, 17:31:55) → queued → landed → shipped
(sender, 17:32:08–11, eef3d55) → walked by the judge (17:32:50) → closed (17:33:09). The minor then closed the
judge's fix row correctly: r10 released at 17:32:28 with evidence `{"settled_by": "r11", "why": "docs fix delivered
by r11 (eef3d55)"}` — **F26 did not recur** (no `offledger`). But the broken row r9 `feat/2048-docs-exe` still stands
`shipped`, broken, with the judge's wait "I re-walk once [r10] ships", and since 17:33 the views raise
`broken_unfixed … and no fix row is open`: the fix link runs r9 ← r10, r10 is released, and nothing follows its
`settled_by` to r11. No move changed r9's mover, so no letter told the judge to re-walk. At 17:34:06 the orchestrator
was `blocked / waiting` with its `ask` hook fired at 17:33:16 — it put a question to the person, presumably about
this. Fix: a fix row released `--settled-by` a delivered row counts as delivered for its broken row
(`broken_unfixed`, the judge's `_fixed`), and the release prints a letter for the judge to re-walk.

G10. **bug — a deadlock: the broken row cannot be walked again, by construction.** At ~17:36 the judge tried
`walked` on r9 and was refused by `judging.walked`: `_fixed` counts only fix rows linked by `fixes` and delivered;
r9's only fix row, r10, is `released` (settled by r11), so the refusal is "broke at …; walk it again once its fix row
is delivered" — a fix row that will never be delivered. The judge recorded a wait on the orchestrator at 17:36
("walked on r9 is refused by judging.py:83 (fix row r10 released, fix came as r11); --skip-event cannot skip it, it
is not an event script"). There is no legal way out: `release` is illegal after `shipped`, `broke` would file yet
another fix row, and `walkable` does not touch the broken check. The fleet did everything right with the moves it
had — the gap is G6 → G7 → G9 compounding. Fix (with G9): `_fixed` follows `settled_by` from a released fix row to
the delivered row that settled it, and requires that row's merge in the build.

G11. **obs — the product works, built on the person's machine; the fleet changed one requirement.** At ~17:52 the
person built `dist\game2048.exe` on Windows with the fleet's `build_exe.bat` / `docs/BUILD.md` (PyInstaller does not
cross-compile, so the Linux VPS could not build it; the fleet said so in BUILD.md and marked the exe as unverified)
and played it: it works. The person had asked for control by the mouse cursor; the fleet built keyboard control
(arrows / WASD) instead, which the person found better. Whether that change was put to the person before it was
built (the orchestrator's one `ask` at 17:22:08) is not visible from outside; a requirement changed on the fleet's
own judgment should be one of the questions the orchestrator puts to the person, and its answer should be recorded.

G12. **bug — `fleet down` releases the seats of two live sessions without stopping them.** At 17:54 the census
listed `main session 2` as `done / idle` and `orchestrator 2` as `done / busy` (its background `watch --wait`
running); `flotilla fleet` called both "not running", and `fleet down` released their post rows with "(it was not
running)" and left both processes alive — they stood in the census until stopped by hand (`claude stop d1ab111c`,
`claude stop b59c9a39`). `retire._running` treats census `state == "done"` as gone, but a background session whose
turn is done is still a live process, and may hold a background task. The census entry is the only liveness there
is: a session listed at all is running. Fix: `_running` = listed in the census, whatever its state; `fleet` shows
the state.

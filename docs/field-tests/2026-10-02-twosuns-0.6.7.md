# Field test: flotilla 0.6.7 on twosuns (auto mode), 2026-10-02

The person continues work on twosuns after updating it from 0.3.3 to 0.6.7. The profile on trunk (`3dd365f`) gained
`[fleet] name = "twosuns"` and `[tests] setup_command = "npm ci"`; permission mode `auto`. No live session in the
project when the test began; trees kept by the 2026-10-02 cleanup (`twosuns-main-12`, `-13`, ...) are still there.

## Findings

W1. **friction - `/flotilla:spawn` does not offer "this session leads".** In an already onboarded project the person
opened a fresh session, ran `flotilla doctor` (all ok) and the session noted it holds no post. The recommended way
to lead a fleet - `flotilla spawn --lead`, then `--fill` on the next message - is offered only by onboarding's last
step. `/flotilla:spawn` with no arguments raises the default composition with a background orchestrator, and
nothing mentions `--lead`; a person who onboarded yesterday cannot find the recommended path today. Fix direction:
`/flotilla:spawn` with no arguments asks the same question onboarding asks - this session leads (recommended), a
background orchestrator, or a named composition - and walks the lead path the onboarding skill describes.

W2. **friction - "tier `npm` has never run green on this machine" is a dead end.** The person ran `/flotilla:onboard`
in the onboarded project; the skill kept the profile and reported `flotilla onboard check`'s one finding, exit 1. The
person asked to fix it; the session ran `npm ci` and then read flotilla's source (`onboard/check.py`, `firstrun.py`)
for a command that records a green run. There is none: measurements are written only by `flotilla onboard write`,
which rewrites the profile, and a green receipt does not record them. The finding names no next step and has none;
it also matters beyond the check - the lane's ceiling for receipts is derived from measured tier times and falls back
to half an hour without them. Fix direction: a green tier in a receipt records its time as the measurement, and the
finding says "measured by the first green receipt" (or names a command that measures without rewriting the profile).
How it ended: `onboard write --force` stopped on unanswered questions; the session put the choice to the person and,
on "record the measurement", called `flotilla.onboard.firstrun.save_measurements` from Python with the time of its
own green run (141.8 s). `onboard check` then passed. So a person fixing a finding flotilla reports had to have a
session import flotilla's internals - about six minutes and a full suite run spent on a line of state.

W3. **defect - a fleet without an orchestrator, raised with no word about it.** W1 played out: the person ran
`/flotilla:spawn` (0.6.7's skill), which used `--default`. twosuns' default composition, written at its onboarding
on 0.3.x, is `main = 1, review = 1, judge = 1` - no orchestrator, no sender. Three seats rose
(`twosuns-main session 1`, `twosuns-review session 1`, `twosuns-acceptance judge 1`), announced themselves to each
other and wait for work that only an orchestrator routes, while the person's session `twosuns-7c` holds no post.
Neither the dry run nor the launch said that nobody leads the fleet. (Seat names are right: project-prefixed,
numbered from 1 in the new series.) Fix direction: spawn warns - and the dry run says first - when the fleet it
leaves has no live orchestrator and no recorded lead, naming `flotilla spawn --lead`; `onboard check` reports a
default composition without an orchestrator; and 0.6.x's onboarding already always includes one
(`suggest_composition`), so only profiles written before it are hit.

W4. **friction (minor) - the memory floor's question recommends not raising the fleet at all.** 3424 MB free, three
seats at ~800 MB each would leave 1024 MB under the 2000 MB floor; the session put "Don't raise (Recommended)" first,
and the person chose `--anyway`. The warning is right; whether the recommendation should be "raise fewer" is open.

## What 0.6.8 does

- W1, W3: `/flotilla:spawn` with no arguments asks who leads, "this session" first; `spawn` prints a `gap:` line when
  nobody would lead the fleet or nobody would merge, and the skill turns it into a question; `onboard check` names a
  default composition without an orchestrator or a needed sender (decision 212).
- W2: the first green receipt measures a tier this machine never measured; the check's finding says so (decision
  213).
- W4 waits: whether the memory floor's question should recommend raising fewer seats rather than none.

W5. **friction - a profile change on trunk becomes fleet work nobody can close.** The planner (outside the fleet,
with the person's yes) committed `3dd365f` straight to trunk: two lines in `.flotilla/project.toml`. The fleet
found it as work that reached trunk without the ledger; the orchestrator assigned the reviewer to read it, the
reviewer read it ("in order") and tried `work vouch main`, refused ("no open ledger row for `main`"), and the
orchestrator worked out that only `offledger`, a sender's move, closes it - and the fleet has no sender (W3). Four
messages and two sessions' turns, and the finding stays open. The same would follow `flotilla onboard publish`, the
sanctioned way to change the profile. Fix direction: a trunk commit that touches only `.flotilla/` is the profile,
not product work - the fleet does not raise it as off-ledger; or `onboard publish` records it on the ledger as it
pushes.
Later the same hour: the orchestrator raised a sender (`spawn -s 1`) to close it, and `work offledger main --merge
3dd365f --witness ...` was refused the same way - offledger records a *row's* branch reaching trunk, and a direct
commit has no row. So `direct_commit` (ledger/findings.py) is a finding no move closes: `vouch` and `offledger` both
want an open row for the branch, and trunk never has one. Revised fix direction: not to exempt `.flotilla/` -
the profile and the posts are what every session obeys, so a direct change to them is exactly what a reader should
read - but to give the finding a closing move: a reader vouches for a direct trunk commit (`work vouch <trunk>
--commit <sha>` recorded without a branch row), and the finding's text names that move.
Third try: `work inbatch chore/flotilla-profile-0.6 --commit 3dd365f ...` refused with "already on origin; work that
reached trunk outside the ledger is recorded with offledger" - and offledger refuses for want of a row. The refusals
send each other in a circle. The orchestrator stopped the fleet's attempts and carried it to the person as a
flotilla defect (correctly). Cost so far: about ten messages and three sessions' turns over two lines of profile.

W6. **friction - a profile commit invalidates the judge's walk of an identical build.** The judge walked
`feat/melancholy` on build `ab7c81c` and recorded `work walked --build ab7c81c`; refused: "the deployed build is
3dd365f ... walk what is deployed". `3dd365f` is the profile commit of W5 - nothing the player sees changed. The judge
rebuilt `3dd365f`, checked `REVISION.txt`, walked again and recorded it: one rebuild and one walk spent on two lines
of `.flotilla/project.toml`. Fix direction: `walked` accepts a build whose difference from the deployed revision lies
only in `.flotilla/` (the fleet's rules, not the product), saying so.
(Seen working the same hour: `watch` raised `mover_gone` for row r138, whose owner from the previous fleet had
closed; the orchestrator adopted it to `twosuns-main session 1`, which closed it - the adoption path did its job.)

W7. **friction (minor) - `flotilla lane status` does not exist.** The judge, waiting for the lane behind the main
seat's frame runs, guessed `flotilla lane status` and got argparse's "invalid choice: 'status'"; the status is the
bare `flotilla lane`. Then it tried `flotilla lane stop` and was correctly refused ("no run in the lane is twosuns-
acceptance judge 1's; held: b928 (twosuns-main session 1) - ask its holder"). Fix direction: accept `lane status`
as the bare command. (The wait itself is the lane contention measured in the slowdown report: the main seat queued
three frame and bench runs with ceilings of 1500-3000 s.)

## What 0.6.9 does

- W5: a reader closes a direct commit on trunk with `work vouch <trunk> --commit <sha>`; the finding and the refusals
  of `offledger` and `inbatch` name it (decision 214).
- W6: `walked` accepts a build that differs from the deployed one only in `.flotilla/` (decision 215).
- W7: `flotilla lane status` (decision 217).
- The person's proposal on orphaned work: a gone session's move comes with the live sessions that could take it and
  the line that hands it over; `broke` stops addressing a dead author (decision 216).

W8. **friction - the reviewer runs the whole suite again over the files the author's receipt already ran.** The
main seat's handover receipt over `3b69d19` was green (1243 tests, about 2.5 min in the lane). The reviewer took the
branch and, as its post says ("run the tiers yourself over that revision"), ran `lane run -- npx vitest run`
directly - outside a receipt, so decision 201's reuse could not apply, and another lane slot went to an answer the
machine had already measured over the same files. The reviewer's independence is in reading and in injections, not
in a second run of the same tests on the same machine. Fix direction: the reviewer runs the tiers through
`flotilla receipt run --purpose handover --tree <home tree>`, which reuses a green tier over the same files and runs
what differs; the post says why.

W9. **defect - in auto mode, Claude Code's classifier refuses the sender's push of reviewed work.** The far-horizon
row r183 was accepted by its reader on `3b69d19`; the sender queued it, merged it `--no-ff` without conflicts
(`6055139`), and its push receipt was green - reused, not run again ("green over the same files at 3b69d19", W8's
reuse working). Then `git push origin HEAD:main` was denied: "Permission for this action was denied by the Claude
Code auto mode classifier. Reason: [Merge Without Review]". The classifier sees a session merging into main; it does
not see the ledger's review, and flotilla's own push guard (receipt over the pushed revision) is invisible to it.
The sender did right - recorded a wait on the person and told the orchestrator - but in auto mode, the default since
0.6.1, every delivery to trunk would wait on the person. Fix direction: to be found in Claude Code's auto mode
configuration (`autoMode.allow` / `environment`, and which settings scopes it reads), so the classifier knows a
sender's push in a flotilla fleet carries reviewed work - without widening it beyond that push.
